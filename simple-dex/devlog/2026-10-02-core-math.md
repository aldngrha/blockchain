# 2 Okt 2026 - AMM: Core Math Implementation

> Task roadmap: "Implement fungsi math AMM: getAmountOut() dengan formula x*y=k dan fee 0.3%." Lanjutannya: fuzz tests untuk math dan pastikan invariant k selalu terjaga setelah setiap swap.

## Apa yang dikerjakan

- Implement `src/AMMLibrary.sol` (library pure, internal): `getAmountOut` (fee 0.3%, dikodekan 997/1000), `getAmountIn` (invers, ceil +1 wei), `quote` (rasio reserve untuk LP math), `sqrt` (Babylonian, floor).
- Implement `test/AMMLibrary.t.sol`: vektor eksak hasil hitung manual (python), fuzz properti (never drains pool, monotonic, product never decreases, round-trip, quote proportional, sqrt bounds), revert cases. Di akhir hari suite library berisi 18 test, semua hijau.
- Vektor eksak sengaja dihitung manual dengan python (pembagian integer yang sama dengan EVM), BUKAN dikutip dari run library-nya sendiri, biar verifikasinya gak sirkular. Natspec test mencatat ini.
- Menemukan (dan mendokumentasikan) satu perilaku math yang penting via fuzz failure: overflow di luar domain. Detail di bawah, cerita lengkapnya juga ada di `docs/security-review.md` section integer precision.

## Masalah & Solusi

### Fuzz round-trip gagal: panic 0x11 di getAmountOut (kejadian nyata, bukan hipotesis)

- Masalah: fuzz test `testFuzz_GetAmountIn_ConsistentWithGetAmountOut` gagal dengan panic 0x11 (arithmetic overflow). Fuzzer memberi counterexample asli: `amountOut = 1329227995784915872903807060280344572` (sekitar 2^120), `reserveIn = 10756` (mungil), `reserveOut = 1329227995784915872903807060280344574`. Dihitung eksak: `getAmountIn` menghasilkan `requiredIn = 7170098456701381709605490842715840630107` (sekitar 7.17e39, sekitar 1.38 juta kali 2^112), dan round-trip ke `getAmountOut` meledak di perkalian internal `amountIn * 997 * reserveOut` (sekitar 9.5e78, melewati 2^256 yang sekitar 1.158e77).
- Kenapa: reserveIn mungil relatif terhadap amountOut membuat requiredIn meledak keluar dari domain. Konvensi Uniswap v2 pakai reserves uint112 PERSIS supaya `amountIn * 997 * reserveOut <= 2^112 * 2^10 * 2^120 < 2^256` dan produk internal tidak pernah overflow. Rumusnya sendiri BENAR dalam domainnya; yang kurang adalah dokumentasi domain.
- Solusi: math TIDAK diubah. Tiga langkah: (1) fuzz round-trip dibatasi domain dengan `vm.assume(requiredIn <= type(uint112).max)`; (2) dua test corner baru di `test/AMMLibrary.t.sol`: `test_GetAmountIn_RoundTripOutsideDomainPanics` yang mengunci perilaku di luar domain secara eksplisit pakai counterexample asli (expectRevert arithmeticError), dan `test_GetAmountIn_RoundTripAtDomainEdge` yang membuktikan corner dalam domain tetap round-trip berkat ceil +1; (3) natspec DOMAIN note di `AMMLibrary.getAmountOut` (src/AMMLibrary.sol). Panic = failure-safe: revert, gak ada state change, gak ada dana pindah.
- Pelajaran: fuzz failure di luar domain bukan bug math yang harus di-patch, tapi kontrak dokumentasi yang belum tertulis; kunci perilakunya dengan test eksplisit supaya tidak jadi skip yang diem-diem.

### forge-std versi baru tidak lagi me-reexport StdError

- Masalah: mau pakai `stdError.arithmeticError` untuk expectRevert panic, kompilasi gagal karena `stdError` tidak dikenal walau `forge-std/Test.sol` sudah di-import.
- Kenapa: forge-std versi baru tidak lagi me-reexport `StdError` dari `Test.sol`, jadi `stdError` harus di-import eksplisit dari `forge-std/StdError.sol`.
- Solusi: tambah `import {stdError} from "forge-std/StdError.sol";` di `test/AMMLibrary.t.sol` (ada komentar di file yang menjelaskan ini).
- Pelajaran: upgrade dependency diam-diam mengubah apa yang diekspor; error kompilasi yang tampak aneh biasanya jujur bilang penyebabnya kalau kita baca simbol yang hilang.

### Corner pertama untuk test domain boundary salah memilih angka

- Masalah: counterexample buatan pertama untuk menguji domain boundary pakai `amountOut == reserveOut`. Ekspektasinya sampai ke overflow, ternyata revert-nya `InsufficientLiquidity`, jadi test-nya menguji guard yang salah.
- Kenapa: `getAmountIn` menolak `amountOut >= reserveOut` SEBELUM sempat menghitung requiredIn, jadi konfigurasi itu tidak pernah sampai ke jalur overflow. Guard berjalan lebih dulu, dan itu perilaku yang benar.
- Solusi: geser satu langkah: pakai `amountOut = reserveOut - 2` (dari counterexample asli fuzz), yang lolos guard dan benar-benar menghasilkan requiredIn raksasa lalu panic di getAmountOut. Itu yang dikunci `test_GetAmountIn_RoundTripOutsideDomainPanics`.
- Pelajaran: saat menulis test untuk mengunci satu perilaku, pastikan corner-nya lolos semua guard yang lebih dulu; revert di tempat lain berarti test menguji hal yang salah.

### Jangan kutip vektor eksak dari run kontrak yang dites

- Masalah: godaan menulis vektor test dengan menjalankan fungsi library lalu menyalin hasilnya. Itu memastikan test hijau, tapi gak membuktikan apa-apa (testing the code against the code).
- Kenapa: vektor eksak nilainya justru sebagai prediksi independen.
- Solusi: semua vektor (9066108938801491315, 987158034397061298, 1215942629948532819, round-trip getAmountIn = 10e18 persis) dihitung manual dengan python integer division sebelum test ditulis; natspec test mencatat asal hitungannya.
- Pelajaran: oracle independen (python isqrt/div) adalah syarat test yang bermakna; hijau dari sirkularitas itu palsu.
