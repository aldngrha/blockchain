# 26 Sep 2026: Frontend Voting UI + Verifikasi Full Flow

> Task roadmap: "Sab 26 Sep, SABTU, Project 2: Frontend, Voting. Voting interface: For / Against / Abstain dengan tombol. Tampilkan voting power user (delegated tokens). Disable vote kalau sudah vote atau proposal tidak active. Konfirmasi transaksi dengan loading state."

## Apa yang dikerjakan

- Voting interface di halaman detail: tiga tombol (Vote For / Vote Against / Abstain) yang manggil `castVoteWithReason`, plus input reason opsional yang tersimpan on-chain di event `VoteCast`.
- Voting power yang ditampilkan adalah `token.getPastVotes(user, snapshot)` (bukan `getVotes` sekarang), dengan penjelasan snapshot di UI.
- Semua kondisi disable vote punya teks alasan eksplisit: sudah vote (`hasVoted`), proposal bukan Active, voting power 0 di snapshot (dibedakan: gak punya token / belum delegate / delegate terjadi setelah snapshot), atau masih ada tx lain jalan.
- Riwayat vote per proposal dari scan log `VoteCast` (voter, pilihan, weight, reason, blok).
- Aksi per state di detail: queue (Succeeded), execute (Queued, disabled sampai eta lewat), cancel (proposer, Pending). Tx states: idle / confirm di wallet / nunggu blok / sukses / error, revert di-parse jadi pesan manusiawi, rejection wallet dibedakan.
- Verifikasi full flow pakai smoke test node (hapus setelah jalan): anvil sendiri di 8545, deploy stack via `cast --create` dengan wiring role persis deploy script, lalu delegate, propose, vote, queue, execute via jalur encoding yang PERSIS sama dengan hooks UI (`encodeFunctionData`, `keccak256(toBytes(...))`, `parseEventLogs`, `getPastVotes`, `getLogs` per event). Semua cek hijau sampai treasury bayar 0.01 ETH.

## Masalah & Solusi

### Voting power itu snapshot, bukan saldo sekarang (jebakan klasik ERC20Votes)

- Masalah: brief minta "voting power user (delegated tokens)". Versi naifnya manggil `token.getVotes(user)`, tapi angka itu gak menentukan proposal yang lagi jalan.
- Kenapa: ERC20Votes nyimpen checkpoint per blok, dan governor menghitung weight PADA SNAPSHOT: `GovernorVotes._getVotes` memanggil `token.getPastVotes(account, timepoint)` tanpa offset (gw baca source OZ 5.4.0 langsung). Delegasi setelah snapshot gak mengubah weight proposal berjalan, cuma berlaku buat proposal yang dibuat belakangan.
- Solusi: UI menampilkan `getPastVotes(user, snapshot)` sebagai "the number the governor counts", dan bedakan tiga sub-kasus voting power nol di teks disable: gak punya GT sama sekali, punya GT tapi belum pernah `delegate()`, atau sudah delegate tapi setelah snapshot. Form delegate nulis hint eksplisit bahwa checkpoint baru berlaku untuk proposal berikutnya.
- Pelajaran: smoke test membuktikan bedanya: `getPastVotes` di snapshot = 1M GT pas, dan itu yang jadi forVotes di tally.

### State tetap Active walau quorum sudah tercapai

- Masalah: pas smoke test, setelah vote For 1M GT (quorum 40k terlampaui jauh), `state()` masih balikin 1 (Active) dan gw nyaris anggap itu bug.
- Kenapa: baca `Governor.state()`: keputusan Defeated/Succeeded baru diambil kalau `deadline < clock()`. Selama voting period (50400 blok) belum lewat, state resminya tetap Active walau tally udah menentukan.
- Solusi: smoke test mine 50401 blok setelah vote baru lanjut. UI-nya sudah benar dari awal (tombol vote cuma aktif saat Active, dan status badge ngikutin `state()`), tapi ini penting buat ekspektasi user: proposal bisa "sudah pasti menang" tapi masih Active sampai deadline.
- Pelajaran: state machine OZ itu timing-based, bukan outcome-based. Jangan uji state outcome sebelum waktunya lewat.

### `TimelockUnexpectedOperationState` di OZ 5.4 parameternya bytes32 bitmap, bukan uint8

- Masalah: uji execute sebelum eta lewat: tx revert, tapi error gak ke-decode sama ABI gw, balikin raw selector `0x5ead8eb5`.
- Kenapa: gw nulis ABI error dari ingatan versi lama OZ: `TimelockUnexpectedOperationState(bytes32,uint8)`. Di OZ 5.4 parameternya `bytes32 expectedStates` (bitmap, pola yang sama dengan `GovernorUnexpectedProposalState`). Selector-nya beda, jadi decoder gak match.
- Solusi: `cast keccak "TimelockUnexpectedOperationState(bytes32,bytes32)"` = `0x5ead8eb5`, cocok. Perbaiki ABI error di `src/abi.js` (error timelock perlu ada di ABI UI karena subcall timelock di `governor.execute` gak di-wrap, revert data-nya nge-bubble mentah ke wallet).
- Pelajaran: error entry di ABI itu decoder, bukan formalitas. Selector gak cocok = pesan error mentah buat user. Dan lagi: sumber kebenaran itu source/artifact, bukan ingatan (ini pola yang sama dengan field `signatures` kemarin).

### Queue/execute/cancel gak bisa dipanggil dari proposal id doang

- Masalah: tombol Queue butuh `queue(targets, values, calldatas, descriptionHash)`, tapi yang gw punya di halaman detail cuma id.
- Kenapa: governor nge-hash ulang payload buat derive id; gak ada cara balik dari id ke payload. Payload cuma ada di event `ProposalCreated`.
- Solusi: ambil payload dari cache scan; `descriptionHash = keccak256(toBytes(description))` dari deskripsi yang tersimpan, dan smoke test membuktikan hasil `hashProposal` on-chain persis sama dengan id dari event. Kalau payload gak ada di cache (log ke-prune, cache kehapus), tombol diganti penjelasan "payload not in cache, rescan or use the subgraph" alih-alih tombol yang pasti gagal.
- Pelajaran: metadata dari event itu bagian dari state UI yang wajib ada, bukan sekadar keterangan. Subgraph jadi makin jelas kenapa dibutuhkan.

### Race read-setelah-write di smoke test (dan kenapa UI gak kena)

- Masalah: begitu tx queue sukses, re-read `state()` langsung masih balikin state lama (Succeeded), padahal beberapa detik kemudian on-chain udah Queued.
- Kenapa: script linear nulis dan baca nyaris di tick yang sama; read-nya bisa mendarat di blok sebelumnya.
- Solusi: re-read dengan retry pendek sampai state settle di smoke test. UI gak punya pola ini karena update state lewat TanStack Query yang di-refetch oleh event watcher dan polling, bukan di tick yang sama dengan write.
- Pelajaran: jangan bandingkan script uji linear dengan UI event-driven; yang perlu dijamin UI adalah refetch-nya terpicu, bukan kecepatan satu kali baca.
